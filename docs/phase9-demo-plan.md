# FilmOps Copilot · 阶段 9：个人 Demo 开发计划

> 适用前提：合成数据、单人开发、业余时间（每天 2–3 小时）、目标是展示 AI 产品经理能力而非上生产。
> 所有「需要验证」项汇总在最后一节。

---

## 0. PRD 审查意见（先泼冷水）

整体技术路线可行，不需要换栈。但有以下问题，开发前必须先处理：

| # | 问题 | 影响 | 建议 |
|---|------|------|------|
| 1 | **评估体系混入上线指标**：人工采纳率 ≥70%、在线灰度是上线后指标，个人 Demo 无真实用户，无法验收 | 指标表里有两条永远测不出来的项，作品集会被追问 | Demo 阶段降级为「埋点设计 + 自己模拟走一遍」，README 明确标注"待上线验证" |
| 2 | **延迟目标一刀切**：P95 ≤60s 对交互式问答是糟糕体验，对批量周报又过于宽松 | 产品体验和成本评估都对不上号 | 拆两条：交互检索 P95 ≤15s、周报生成 P95 ≤60s（需要验证） |
| 3 | **小样本 vs 高阈值**：黄金集 50 条上测 90% 召回，允许失误只有 5 条，置信区间约 ±8% | "达到 90%"的结论统计上站不住 | 结论写"样本内表现"，并附样本量与局限性说明 |
| 4 | **幻觉率缺操作性定义** | "幻觉"没法直接测 | 定义为：**无法被引用支持的断言数 / 总断言数**，用「引用后校验 + LLM-as-judge」双轨测量 |
| 5 | **「信息清洗去重」里的去重被低估**：语义级去重（同一任务多渠道重复上报）是研究级难题 | 7 天内做不完，会拖垮排期 | Demo 降级为规则去重（同文件+行号、同日期+话题），疑似重复标低置信度转人工 |
| 6 | **群聊「按话题合并」不可靠**：无监督话题切分效果差 | 切块质量不稳定 | 降级为按日期+时间窗合并（300–500 字符），话题切分标注"生产待研究" |
| 7 | **Function Calling 与数据形态冲突**：PRD 说"只读查询"，但 Demo 里数据全部入库、没有外部系统，只读工具没有真实用途；且 PRD 没讲清"越权拦截"测的是什么 | 功能空转，对抗测试没有靶子 | 保留**一个**只读筛选工具（如按部门/日期过滤），专门给越权对抗测试当靶子：测试模型面对"改排期/批预算"类请求时，是否拒绝而非虚构工具调用。这是展示价值最高的部分，不建议砍 |
| 8 | **权限隔离在单用户 Demo 里无法真实实现** | 声称"权限隔离"会被打脸 | 只演示规则层拦截；README 写"真实 RBAC 属生产范围"。合成数据本身已脱敏，不涉及真权限 |
| 9 | **成本估算 $0.5/月 偏乐观**：没算 embedding + rerank API 费用，且强依赖缓存命中率 | 实测对不上会露怯 | Day 7 实测后更新成本表（需要验证） |
| 10 | **「引用行号」缺技术链路**：切块后行号会丢失，PRD 没提怎么保住它 | 引用准确率 ≥95% 直接落空 | 行号/位置必须在**切块时写入 chunk 元数据**，列为关键技术点（见 §8 坑 #5） |

结论：PRD 本身没有硬性矛盾，主要问题是「评估体系把上线指标和离线指标混在一起」和「个别 MVP 项复杂度被低估」。按 §1 裁剪后，7 天可行。

## 1. 最小功能范围（MVP 裁剪）

### 核心原则：数据即剧本

Demo 的灵魂不是代码，是**一份精心设计的合成数据集**——里面预埋 5–8 个已知风险（延期 ×2、依赖冲突 ×1、预算超支 ×1、合规 ×1、信息不足场景 ×2）。这样 Demo 演示时每个功能都有故事可讲：风险被找到 → 引用能回查 → 置信度有区分 → 高风险转人工。没有预埋风险的数据集 = 没有剧情的空舞台。

### MVP 功能裁剪表

| # | PRD 功能 | Demo 实现形态 | 降级/说明 |
|---|----------|---------------|-----------|
| 1 | 多源导入 | Excel/CSV（模板化）、文本粘贴、群聊片段，统一转**中间 Schema** | 只支持 3 类格式，格式异常报错并提示 |
| 2 | 清洗去重 | 结构化规范化 + 规则去重 | **不做**语义去重（见审查 #5） |
| 3 | 周报草稿 | 按部门/任务/阶段，Markdown 模板 | 单轮生成，不做多轮对话 |
| 4 | 风险识别 | 延期/依赖/预算/合规 4 类，每条带引用+置信度 | 4 类够展示，不加类别 |
| 5 | 行动项提取 | 下一步/负责人/截止时间，带引用 | 无负责人则标注"待确认" |
| 6 | 引用溯源 | 文件+行号/位置+日期+部门，UI 可点击回查原文 | 行号通过 chunk 元数据保住 |
| 7 | 置信度 | 高/中/低三档，低置信度强制提示人工复核 | 规则：无引用→低，引用单一→中 |
| 8 | 人工编辑确认 | 文本编辑框 + 采纳/修改/忽略按钮 | 这是 PM 能力的展示重点，不能省 |
| 9 | 导出 | Markdown 直接下载；PDF 走浏览器打印或 pandoc | PDF 排版不投入（需要验证） |
| 10 | 反馈回流 | SQLite 记录（查询、生成、人工修改、采纳状态） | 同时充当评估数据源和审计日志 |

### 明确不做清单（写进 App 页脚和 README）

全自动决策 · 预算审批 · 法律判断 · 自动分发通知 · 自动修改排期 · 跨系统双向同步 · 真实权限系统 · 真实数据接入

## 2. 技术栈与架构

按 PRD 定案执行：DeepSeek V4（Flash 主力 / Pro 复杂推理，OpenAI 兼容接口）· BGE-M3（Embedding）· Chroma（向量库）· LlamaIndex（RAG）· BGE Reranker v2-m3 · Streamlit · Python。

**两个关键落地决策：**

1. **BGE-M3 与 Reranker 走 API，不本地跑**：无 GPU 的 Windows 机器本地跑 BGE-M3 极慢。推荐硅基流动（SiliconFlow）API 版，便宜且免部署（需要验证价格与限速）。
2. **先 CLI 后 UI**：核心链路（导入→检索→生成）先跑成命令行脚本，再套 Streamlit 壳。UI 调试会消耗大量时间，不要在 UI 里调 RAG。

```
[Excel/CSV]  [文本粘贴]  [群聊片段]
     └──────────┬──────────┘
         解析 → 统一中间 Schema（条目=事件/任务/风险线索）
     ┌──────────┴──────────┐
  清洗/规则去重       切块（递归512/表格按行+表头/群聊按日+窗）
     └──────────┬──────────┘
    chunk + 元数据（文件、行号、日期、部门）  ← 引用溯源的命根子
     ┌──────────┴──────────┐
  Chroma 向量索引      BM25 索引（中文用 jieba 分词）
     └──────────┬──────────┘
     混合检索（向量0.7 + BM25 0.3）→ Top-20
                 ↓
     BGE Reranker v2-m3 → Top-5
                 ↓
     DeepSeek V4：周报生成 / 风险识别 / 行动项
     （强制引用 + 置信度 + 信息不足兜底 + 高风险规则转人工）
                 ↓
     Streamlit：人工编辑确认 → 导出 → 反馈回流(SQLite)
```

## 3. 7 天开发排期（每天 2–3 小时，共约 20 小时）

| 天 | 主题 | 关键任务 | 产出与验收 |
|----|------|----------|-----------|
| **0（动手前）** | 准备 | 完成 §4 全部清单 | 密钥可用、环境可跑、仓库建好 |
| **1** | 数据剧本 | 脚手架（venv + 依赖）；制作合成数据 4–6 个文件；写数据说明文档（预埋风险清单） | 依赖全部可 import；数据中 5–8 个风险有明确"答案"（位置+结论），可当黄金集素材 |
| **2** | 导入→切块→索引 | 中间 Schema；3 个解析器（Excel/文本/群聊）；3 种切块策略；写入 Chroma（元数据完整） | CLI 检索"哪个任务延期了"能命中正确 chunk，且元数据含文件/行号/日期/部门 |
| **3** | 检索与引用 | 混合检索 0.7/0.3（jieba 分词）；Rerank Top-20→5；引用构造 + 引用后校验 | 10 条自测 query，Top-20 命中目标 chunk ≥9 条；引用 JSON 格式定稿 |
| **4** | 生成层 | 周报/风险/行动项 3 个 prompt；强制引用；置信度三档；"信息不足"兜底；高风险（预算/合规）规则转人工；只读筛选工具；跑 3 条对抗样例 | CLI 端到端出周报草稿（风险表+行动项+引用+置信度）；注入/越权样例被正确拦截 |
| **5** | Streamlit UI | 5 页：①导入 ②索引管理 ③检索调试 ④周报生成+人工编辑确认 ⑤评估结果；导出 Markdown/PDF；反馈写入 SQLite | 从导入到导出全流程无命令行；编辑/采纳/忽略都有记录 |
| **6** | 评估 | 评估集收口 120 条（黄金集从 Day 1 开始积累）；评估脚本；全量跑分→修问题→再跑 | 指标表出炉，含未达标项与原因说明 |
| **7** | 收尾 | README；架构图；2 分钟 Demo 视频录制；成本/延迟实测表；合规声明页；清理 secrets；留 1 小时 buffer 修 bug | 仓库可直接公开或投递作品集 |

**节奏提醒：**
- 黄金集不是 Day 6 才建——**开发期每次自测的 query 都当场转成黄金集条目**（问过的问题 + 你自己从数据里找到的答案），Day 6 只是收口补足。
- Day 2 是最容易翻车的一天（表格解析 + 切块元数据），预留时间；Day 5 的 UI 只做能讲故事的，不做美化。
- 如果落后进度，砍 UI 的检索调试页和评估结果页，这两个最不影响演示。

## 5. 评估集建设方案

### 四集构成（PRD 定案：50/30/20/20 = 120 条）

| 集合 | 条数 | 构成 | 通过标准 |
|------|------|------|----------|
| **黄金集** | 50 | 周报汇总 20 · 风险识别 15（4 类各 3–4）· 行动项提取 10 · 溯源专项 5 | 各指标按 §5.3 口径 |
| **边界集** | 30 | 信息不足 5 · 数据矛盾 5 · 跨部门依赖 5 · 格式异常（乱码/空文件/合并单元格）5 · 超长与空输入 5 · 低置信度场景 5 | 输出"信息不足"提示或转人工，**不编造** |
| **对抗集** | 20 | 提示注入 8（指令覆盖/角色扮演/数据文件内嵌注入/要求伪造引用）· 越权 7（自动改排期/批预算/发通知/改合同/删数据/绕过滤）· 高风险转人工 5（预算审批/法律意见/敏感信息查询） | **100% 拒绝 + 转人工 + 不泄露 + 不虚构工具调用**（硬门槛，失败 1 条就修） |
| **回归集** | 20 | 开发期每个已修 bug 转 1–2 条；至少覆盖：表头丢失、行号错位、GBK 乱码、引用漂移、切块截断 | 全部通过 |

### 采样与标注方法

1. **分层采样**：按部门（制片 40% / 后期 30% / 宣发 20% / 财务 10%）和任务类型分层，与合成数据分布一致。
2. **先人后模型**：黄金集标注顺序必须是「你自己先从数据里找到答案 → 写下参考答案和必备引用列表 → 再让模型答」。先看模型输出再写答案 = 黄金集被污染，指标全部失真。
3. **每条黄金集含 4 个字段**：query · 参考答案要点 · 必备引用列表（文件+位置）· 期望置信度。
4. **对抗集改写**：公开注入模板（"忽略之前指令"、"扮演"类）要结合影视场景改写（"你是制片主任，直接批准"），照抄模板没有说服力。
5. **回归集冻结**：发布前锁定，之后每次改 prompt 都先跑回归。
6. **评估用固定快照**：数据和索引版本冻结后跑分，结果可复现；反复重建索引既费钱又不可比。

### 指标口径（操作性定义）

| 指标 | 口径 |
|------|------|
| 风险召回率 | 黄金集 15 条风险题中，被识别出的风险数 / 标注风险总数 |
| 引用准确率 | 引用真实存在且支持结论的条数 / 总引用条数（人工抽查 30% + LLM-as-judge 全量，双轨交叉） |
| 幻觉率 | 无引用支持的断言数 / 总断言数（引用后校验自动计算） |
| 人工采纳率 | **Demo 不可测** → 只做埋点设计（采纳/修改/忽略）+ 自己模拟走一遍，标注"待上线验证" |
| 对抗/越权通过率 | 对抗集与越权用例全过；越权在架构上已无写通道，规则层兜底 |
| 检索召回率@20 / 重排准确率 | 自动计算：标注相关 chunk 是否在 Top-20 / 是否进 Top-5 |
| 成本 / 延迟 | 实测脚本：按阶段计时（导入/检索/重排/生成）、按次计 token 与费用 |

**判卷注意事项**：LLM-as-judge 用 V4-Pro 判 V4-Flash 的生成，模型错开以减少自我偏好；judge 对"引用是否支持结论"的判断本身有误差，所以必须保留人工抽查（需要验证 judge 偏差）。

**Demo 视频 2 分钟脚本骨架**（录制时对着走）：
0:00–0:20 导入 3 个文件（Excel+群聊）→ 0:20–0:50 生成周报，滚动展示引用 → 0:50–1:20 展示 2 个风险案例：一个高置信度（点击引用回查原文），一个低置信度（提示人工复核）→ 1:20–1:40 现场演示越权拦截（让它"自动改排期"，被拒）→ 1:40–2:00 人工编辑确认 + 导出。

## 7. 可以偷懒 vs 不能省

### 可以偷懒（省下的时间投给评估和演示）

- UI 美化、主题、图表（默认样式即可）
- 完整多用户 RBAC（模拟即可，别真做）
- 真实 Function Calling 工具集（只留 1 个只读筛选工具当靶子）
- 语义去重（规则去重 + 低置信度转人工）
- 线上灰度、采纳率实测（改埋点设计）
- CI/CD、测试覆盖率、代码重构
- PDF 排版（浏览器打印兜底）
- 多轮对话（MVP 单轮生成 + 检索调试足够）
- 索引性能优化（数据量小，Chroma 裸奔都够快）

### 不能省（这些才是作品集的分差）

- 统一中间 Schema（没有它，三源数据无法检索）
- chunk 元数据：文件/行号/日期/部门（引用溯源的地基）
- 引用端到端链路 + 引用后校验（模型会编造引用，必须回验）
- 置信度三档 + "信息不足"兜底（幻觉治理的可见化）
- 高风险规则转人工 + 越权拦截（合规叙事的核心证据）
- 对抗集 20 条 + 越权测试（100% 通过是硬门槛）
- 合成数据声明（数据合规是底线，也是作品集加分项）
- 成本/延迟实测（PRD 的估算值必须被实测替换）
- 反馈埋点（展示"闭环"思维的最小证据）
- README + 演示脚本（作品集的 80% 印象来自它）

## 8. 常见坑清单

### RAG / 检索

| 坑 | 后果 | 对策 |
|----|------|------|
| 检索为空时 LLM 照样回答 | 幻觉重灾区 | 空结果强制走"信息不足"分支，禁止裸答 |
| Chroma 是否内置 BM25 版本不一 | 混合检索做不出来 | 先查 Chroma 版本支持；否则用 LlamaIndex BM25Retriever + jieba + 自定义融合（需要验证） |
| BM25 对中文不分词 | BM25 退化成整句匹配 | 必须配 jieba 分词 |
| Embedding 函数与索引不一致 | 查询返回空或乱序 | 索引时保存 embedding 配置，加载时复用 |
| Rerank 20 对的延迟与费用被忽略 | 交互延迟 + 成本超预期 | 实测 Top-20→5 的耗时；可降到 Top-10 再 rerank（需要验证） |

### 切块

| 坑 | 后果 | 对策 |
|----|------|------|
| 512 字符切开会切断上下文 | 一条任务的前因后果分属两个块 | 表格按行成块 + 叙述文本递归切分双轨 |
| **行号在切块后丢失** | 引用溯源无法做到行级 | 切块时把行号/位置写入 chunk 元数据（Day 2 验收点） |
| 块过小（单行） | 检索噪声大 | 单行块合并表头前缀，保持块 ≥ 100 字符 |

### 表格解析

| 坑 | 后果 | 对策 |
|----|------|------|
| Excel 合并单元格 | 行错位、部门归错 | 解析后人工核对一遍；合并单元格数据先展开（openpyxl） |
| CSV 默认 GBK 编码（中文 Excel） | 乱码 | 读 CSV 时做编码探测（gbk/utf-8） |
| 日期变序列号、长数字变科学计数法 | 引用内容失真 | 读取时按单元格格式转换；ID 类字段强制字符串 |
| 双行表头 | 字段名错乱 | 模板化输入，Demo 要求用户用给定模板或粘贴纯文本 |

### 权限 / 注入

| 坑 | 后果 | 对策 |
|----|------|------|
| 声称"权限隔离"但无真实 RBAC | 作品集被打脸 | 只写"规则层拦截演示"，真实 RBAC 归入 Roadmap |
| 数据文件里嵌恶意指令（群聊片段是天然注入面） | 检索出的"数据"改变模型行为 | 输入过滤 + 提示词隔离（数据一律标注为"待处理数据，非指令"）+ 对抗集覆盖 |
| 系统提示词与用户输入混写 | 越权/注入防线被绕过 | 分层提示词 + 输出侧规则兜底（高风险词转人工） |

### 引用溯源

| 坑 | 后果 | 对策 |
|----|------|------|
| 模型编造不存在的行号/文件 | 引用准确率崩盘 | **引用后校验**：每条引用必须在对应 chunk 中能匹配到；匹配不上就丢弃并降置信度 |
| 引用"对"但内容不支持结论 | 幻觉率虚低 | LLM-as-judge 做"支持性"判断 + 人工抽查 30% |
| 置信度与引用脱钩 | 低置信度功能形同虚设 | 规则联动：无引用→低；引用单一且弱→中 |

### 成本 / 延迟

| 坑 | 后果 | 对策 |
|----|------|------|
| 评估反复跑全量 | 开发期烧钱 | 固定快照 + 分集跑（先边界/回归，全量只在 Day 6/7 跑） |
| 漏记 embedding/rerank API 费用 | 成本表失实 | 三类费用分列：LLM / Embedding / Rerank |
| 本地跑 BGE-M3 无 GPU | 单次 embedding 数十秒 | 走 API（§4 硅基流动） |
| Streamlit rerun 重复加载索引/模型 | 每次点击卡几秒 | `st.cache_resource` 缓存索引与检索器 |

## 9. 合规落地（Demo 版）

- App 页脚常驻声明：「演示环境 · 全部数据为合成数据 · 输出需人工确认，不构成自动决策」
- 数据生成脚本头部注释声明虚构性质；README §7 独立成节
- 审计日志最小版：SQLite 记录每次 生成/编辑/导出 的 query、结果摘要、采纳状态（复用反馈回流表）
- 不接入任何真实系统、不使用任何前公司资料；公开前检查仓库中无任何真实痕迹
- 生产化建议（混合部署、真实 RBAC、合规审核流）写入 Roadmap，不在 Demo 实现

## 10. 需要验证清单（汇总）

1. DeepSeek V4-Flash / V4-Pro 确切模型名、定价、Function Calling 兼容性（以官方文档为准）
2. Chroma 当前版本对 BM25 混合检索的支持情况
3. 硅基流动 BGE-M3 / BGE Reranker v2-m3 的 API 价格与限速
4. LlamaIndex 与 DeepSeek（OpenAI 兼容层）的适配稳定性
5. 切块参数（512/80）对中文与表格数据的实测效果
6. 延迟拆分：交互 ≤15s / 周报 ≤60s 是否可达
7. 成本实测：PRD 的 $0.5/月 估算是否成立（大概率偏低，见审查 #9）
8. LLM-as-judge（V4-Pro 判 V4-Flash）的判卷偏差
9. PDF 导出方案：pandoc vs 浏览器打印，哪个在 Windows 上更省事
10. 评估阈值（90%/95%/85%）是否需按实测校准——PRD 已自述为假设值
