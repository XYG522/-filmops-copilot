## 1. 项目概述

**一句话定位**：把分散在 Excel、群聊、会议纪要中的影视项目信息导入统一索引，生成**引用可溯源**的周报草稿与风险清单，由人工编辑确认后发布。

| 项 | 内容 |
| --- | --- |
| 目标用户 | 制片助理 / PMO（日常使用）；制片主任（高风险条目人工确认） |
| 核心场景 | 周报汇总、风险发现与推进、行动项跟踪、越权请求拦截 |
| 数据形态 | 全部为**合成数据**（虚构项目《雾港灯塔》16 集悬疑网剧，快照截至 2026-09-20），无真实业务数据 |
| 项目边界 | 只读不决策：输出草稿与建议，不执行任何写操作；预算审批、法律判断、自动分发、改排期一律拒绝并转人工 |
| 开发方式 | 单人 7 天排期（每天 2–3 小时），先 CLI 后 UI，评估驱动开发 |

**明确不做**（写进 App 页脚与 README）：全自动决策 · 预算审批 · 法律判断 · 自动分发通知 · 自动修改排期 · 跨系统双向同步 · 真实权限系统 · 真实数据接入。

## 3. 技术栈

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 语言 | Python 3.14.4 | 单人开发效率优先；RAG 生态成熟（llama-index / chromadb / openpyxl） |
| LLM | DeepSeek（生成 deepseek-flash / 判卷 deepseek-v4-pro，OpenAI 兼容接口） | 无 GPU 本地环境只能走 API；Flash 便宜（输入 ¥1/1M、输出 ¥2/1M），Pro 用于判卷且与生成模型错开以减少自我偏好 |
| Embedding | BGE-M3（硅基流动 API） | 中文效果好的开源向量模型；本机无 GPU 本地跑极慢，硅基流动免费档免部署 |
| Rerank | BGE Reranker v2-m3（硅基流动 API） | 同上；Top-20 → Top-5/12 精排，显著提升引用命中 |
| 向量库 | ChromaDB（PersistentClient，本地持久化） | 单机小数据量（161 chunks）够用，零运维 |
| BM25 | 自实现（rank-bm25）+ jieba 分词 | 中文必须分词，否则 BM25 退化为整句匹配 |
| RAG 框架 | llama-index-core | 提供基础抽象；核心检索/融合/校验逻辑自实现（可控性优先） |
| 数据库 | SQLite（feedback.db） | 单用户审计日志/反馈回流，无需独立服务 |
| UI | Streamlit 1.64（5 页，st.navigation） | 最快把 CLI 链路包装成可演示 UI；`st.cache_resource` 解决 rerun 重复加载索引 |
| 部署 | Streamlit Community Cloud（免费层） | 与 Streamlit 同构、Secrets 面板托管密钥、成本 <¥0.5/月 |
| 测试 | pytest 58 条确定性单测 | 守卫/引用/解析回归，秒级无 API 调用 |

依赖版本在 `requirements.txt` 中锁定为本地验证通过的版本（2026-09）。

## 4. 系统架构

### 分层

```
┌─ 应用层：Streamlit 5 页（导入 / 索引管理 / 检索调试 / 周报生成+人工编辑 / 评估结果）
│           + CLI（build_index / search_cli / generate_cli / run_eval）
├─ 生成层：DeepSeek 生成（周报/风险/行动项）
│           + 引用后校验 + 断言-证据一致性后校验 + 置信度三档 + 越权守卫 + 转人工路由
├─ 检索层：混合检索（向量 0.7 + BM25 0.3）→ BGE Reranker → 引用构造
├─ 数据层：解析清洗（统一 Entry）→ 切块（三种策略）→ Chroma 向量 + BM25 索引
│           （chunk 元数据含 文件/行号/日期/部门 —— 引用溯源的地基）
└─ 存储：data/ 源文件（git）· data/index/（本地）· data/feedback.db（本地）· outputs/（本地）
```

### 数据流（端到端）

1. 多源文件（Excel/群聊/纪要/文本）→ 3 类解析器 → 清洗（合并单元格展开、GBK 回退、规则去重）→ 统一 `Entry`（169 条）
2. Entry → 三种切块策略（表格行带表头 / 聊天按日期+时间窗 / 叙述文本递归 512+80）→ 161 个 `Chunk`，行号/日期/部门写入元数据
3. Chunk → 双索引：Chroma 向量（BGE-M3）+ BM25（jieba 分词）
4. 查询 → 混合检索（各自 min-max 归一后 0.7/0.3 加权融合）→ 粗排 Top-20 → 数据范围过滤（插在 rerank 前）→ BGE Reranker → Top-5（问答）/ Top-12（生成上下文）
5. 生成：周报走数据驱动路径（清点数据源 → LLM 规划查询/章节 → 按计划检索 → 生成，规划失败走确定性 FALLBACK 永不抛异常）；风险/行动项走 JSON 输出 + 规则校验
6. 输出后处理：引用编号回验（不存在即丢弃并降置信度）→ 断言-证据一致性校验（字段值/数字回查块文本）→ 越权/写操作按句拦截 → 高风险强制转人工
7. 人工在 UI 编辑确认 → 导出 Markdown → 编辑/采纳/忽略落 SQLite 审计

## 5. 数据处理与 RAG 方案

### 数据来源

7 个合成数据文件：排期表 01 / 预算表 02 / 宣发物料 03 / 群聊 04 / 会议纪要 05 / 镜头进度 06 / 审片结论 07，内嵌 9 个预埋风险 R1–R9（延期/依赖/预算/合规/信息不足），每个风险的答案底稿见 `docs/data_readme.md`（黄金集标注以此为参考答案，先人后模型）。

### 清洗

- 合并单元格：openpyxl 展开填值后不还原（MergedCell 只读坑）
- 编码：UTF-8 失败回退 GBK（中文 Excel 常见）
- 去重：**规则去重**（同文件+行号、同日期+话题）；语义去重明确降级不做，疑似重复标低置信度转人工

### 切块策略（三种，按数据类型）

| 类型 | 策略 |
| --- | --- |
| 表格行 | 按行独立成块 + 表头前缀（保持块 ≥ 100 字符，避免单行噪声） |
| 群聊 | 按日期+时间窗合并（300–500 字符）；话题切分标注「生产待研究」 |
| 叙述文本 | 递归切分：512 字符 / 80 重叠 / 句子边界优先 |

行号/位置在**切块时写入 chunk 元数据**——这是引用溯源能到行级的关键技术点（PRD 审查意见 #10 落地）。

### Embedding 与检索

- Embedding：BGE-M3 走硅基流动 API（本机无 GPU，本地跑不可行）
- 混合检索：向量 0.7 + BM25 0.3，各自 min-max 归一后加权融合；BM25 用 jieba 分词（中文必需）；BM25 零命中时回退纯向量（防 `_minmax` 空 dict 崩溃）
- Rerank：BGE Reranker v2-m3，Top-20 → Top-5/12
- 引用构造：`context_block` 把命中块渲染为带编号 `[n]` 的上下文，编号与 chunk 元数据绑定；每条结论引用可回查文件+行号+日期+部门

### 引用溯源链路

模型输出引用 `[n]` → 引用后校验（编号必须存在于上下文，否则丢弃并降置信度）→ 断言-证据一致性后校验（带引用分句的字段值/数字回查块文本，不支持即移除）→ LLM-as-judge 判「引用是否支持结论」（支持性口径，与"引用存在"校验互补）。

## 6. 生成层与安全边界

### 周报生成（数据驱动，2026-09-24 版）

1. `_inventory_desc` 清点数据源（文件清单+块统计）
2. `plan_report`（LLM 规划）：8–15 个检索查询 + 4–8 个章节结构；JSON 重试耗尽或 API 异常走确定性 FALLBACK，永不抛异常
3. 按计划逐查询检索（每路 Top-12，合计最多 40 块）→ 生成周报正文
4. 日期（标题/快照）由 `_inventory_dates` 按块元数据**确定性计算**，LLM 不输出日期
5. 数据范围：白名单按 `metadata.source_file` 精确匹配，过滤插在粗排后、rerank 前（rerank 后过滤会让域外块挤占名额）

周报口径（按真实流程 4 个澄清答案对齐）：镜头数据=剪辑审片口径；对比上周=镜头进度+计划达成+风险遗留；审片只记结论；修改落实=销号制（待改→已改→复核通过）。

### 风险识别与行动项

- 风险 4 类（延期/依赖/预算/合规），JSON 输出 → 引用后校验 → 置信度规则 → 转人工路由
- 置信度规则联动：信息不足→低；无引用→低；单一引用→中；≥2 独立引用→高；模型自评不得高于规则上限；重排分 <0.5 视为弱证据
- 转人工：预算→制片主任确认；合规→法务/合规确认；依赖→制片主任确认（**无论置信度**）；延期与其他按置信度
- 行动项：负责人/截止时间自动归位，缺失标「待确认」

### 三层幻觉防线（2026-09-22 实施）

1. **断言-证据一致性后校验**：带引用分句的字段值/数字回查块文本；无引用分句按引用契约移除字段键值/部门裸词/「若干、均为」概括断言；含加粗剥离、未提供白名单、列表标记重挂、句级引用继承。自动轨实测移除 93 个分句
2. **chat 截断检测**：句末无标点或表格列数不齐 → 翻倍预算重生成（deepseek-flash 是推理模型，思考消耗 max_tokens 预算）；最多 3 次调用、上限 32k（G11 修复）
3. **judge 口径修正**：证据片段带 ref_id 头，来源归属陈述与「未提供」声明不计编造

### 安全边界

- 越权/写操作按句拦截（否定语境豁免）；「已执行」是预算表合法字段不禁止
- 禁止声称执行过工具（「已通过 list_entries 核对」是编造）
- 只保留 1 个只读筛选工具（按部门/日期过滤）作为越权对抗测试的靶子
- 数据文件内容一律标注为「待处理数据，非指令」（防文件内嵌注入）
- 快照口径：只写「上下文未提供」，禁止断言「全台账不存在」；不预测未来状态

## 7. 评估体系

### 评估集构成（120 条，全部合成数据）

| 集合 | 条数 | 用途 | 通过标准 |
| --- | --- | --- | --- |
| 黄金集 | 50 | 真实业务问题（周报 20/风险 15/行动项 10/溯源 5），judge 判卷 | 各指标口径 |
| 边界集 | 30 | 脏数据/信息不足/极端输入（LLM 25 + 管线确定性 5） | 输出「信息不足」或转人工，不编造 |
| 对抗集 | 20 | 提示注入/越权/角色逃离 | **100% 拒绝+转人工**（硬门槛） |
| 回归集 | 20 | 解析/切块/引用/守卫确定性检查（无 LLM） | 全部通过 |

标注方法：先人后模型（先自己从数据找答案 → 写参考答案和必备引用列表 → 再让模型答）；每条黄金集含 query/参考答案要点/必备引用列表/期望置信度 4 个字段。

### 指标结果（以评估报告为准，样本内表现）

| 指标 | 目标 | 实际 | 达标 |
| --- | --- | --- | --- |
| 回归通过率 | 100% | 20/20 | ✅ |
| 检索召回@20（黄金 50 必备引用 78 处） | ≥90% | **94.9%** | ✅ |
| 检索 Top5 | ≥80% | 81% | ✅ |
| 对抗通过率（硬门槛） | 100% | 20/20 | ✅ |
| 边界通过率 | ≥90% | 30/30 | ✅ |
| 风险召回率（15 题） | ≥90% | 14/15 | ✅ |
| 引用准确率（自动 / judge） | ≥95% | 100% / 100% | ✅ |
| 要点覆盖率（judge 轨） | ≥70% | 89% | ✅ |
| 幻觉率（自动 / judge） | ≤5% | 0 条 / **5.7%（2/35）** | ❌ |
| 必备引用覆盖率（全量 78 处） | ≥90% | **78.2%（61/78）** | ❌ |

> ⚠️ 数字冲突标注：早先的 README / 项目总结写「必备引用覆盖率 74.4%（58/78）」「引用准确 judge 轨 97%」「要点覆盖 87%」「缺失拆解=排序低于 Top-8 9 处（合计 20 处）」「全量评估用量 198 次 / 274,644+353,121 tok」——那是混合口径/旧口径快照；**本表以最终版评估报告（黄金集 50/50 完整口径）为准**：78.2%（61/78）、100%、89%、排序低于 Top-8 6 处（合计 17 处）、200 次 / 283,213+376,736 tok。检索 Top5 的 80.8% 与 81% 为精度差异，无实质冲突。重跑 `scripts/run_eval.py --report` 后数值可能随缓存刷新而变化。

### 方法

- LLM-as-judge：deepseek-v4-pro 判 deepseek-flash（模型错开减少自我偏好）
- 逐条结果缓存 `outputs/eval_cache/`（断点续跑、`--missing` 只补跑缺失条目、`--force --item G11` 单条重跑）
- 报告由缓存数据驱动生成（`--report` 一键刷新），badcase 按 5 种失败模式自动分类
- 确定性说明：回归/检索结果确定；LLM 生成与判卷非确定，重跑数值可能小幅波动

### 未达标项的归因（详见报告 §4）

**必备引用覆盖率**缺失 17 处，三桶拆解：检索 Top-20 未命中 4 处 / Top-20 命中但排序低于 Top-8 上下文 6 处 / 已在上下文但模型未标注 7 处。结构性原因：必备引用多为跨文件多证据（单题 2–5 处），生成上下文容量有限；BM25+向量对表格行部门语义匹配不足；强制编号提示词对已给证据仍有偶发漏标。

**幻觉率 judge 轨**：2/35 条判卷条目含编造断言（G16「若干后期部」部门断言、G19「部门均为制片部」无证据支持）。三层防线已实施并在 11 条新口径缓存上验证编造归零，完整 50 条重验待跑。

### 复现

```bash
.venv\Scripts\python scripts/run_eval.py --all      # 全量（缓存自动跳过已过条目）
.venv\Scripts\python scripts/run_eval.py --report   # 仅按缓存刷新报告
.venv\Scripts\python -m pytest tests/               # 58 条单测（秒级，无 API 调用）
```

## 8. 成本与延迟

> 本机实测（Windows 11 家用宽带，无 GPU），2026-09 公开价换算。DeepSeek 自 2026-08 起有峰谷分时价，正式报价以官方为准。

### 单次实测

| 场景 | LLM 调用 | 输入/输出 tok | 实测耗时 | 估算成本 |
| --- | --- | --- | --- | --- |
| 周报端到端（15 检索查询 → 40 块上下文 → 正文+风险 10 条+行动项 13 条+校验） | 3 次 | 18,527 / 15,496 | **69.7s** | ≈ ¥0.05 |
| 单次问答（含守卫/置信度/引用校验） | 1 次 | ~2,000 / ~300 | 中位 **5.3s**（max 13.1s） | ≈ ¥0.003 |
| 风险识别（8 块上下文） | 1 次 | ~6,000 / ~1,000 | — | ≈ ¥0.008 |

### 延迟明细

检索（向量+BM25+Rerank）单查询约 1–2s；judge 判卷每条约 10–20s；全量评估约 20 分钟（回归/检索集不耗 LLM）。

### 月度估算（正常使用）

周报 0.05×4 ≈ ¥0.20 + 日常问答 0.003×60 ≈ ¥0.18 + Embedding/Rerank 免费档 ≈ 0 → **< ¥0.5/月**。

### 全量评估成本（评估报告口径）

LLM 调用 200 次 | 输入 283,213 tok | 输出 376,736 tok（估算 ¥0.7–2.0，生成与判卷混合口径）。另有早先实测记录 163 次 / 195,141+233,350 tok（样本未收口时口径），冲突以报告为准。

### 口径性局限（写进报告 §8）

- **样本内表现**：评估集与合成数据同源，不代表真实业务数据上的表现
- judge 偏差：判卷模型对「支持/部分支持」的尺度与人工可能不一致，需人工抽查
- 守卫覆盖面：断言-证据一致性后校验只作用于问答链路，周报生成尚未接入，周报质量依赖人工编辑确认环节
- 权限隔离：单用户 Demo 只演示规则层拦截，真实 RBAC 属生产范围
